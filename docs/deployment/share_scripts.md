# Sharing Your Recipes

Once a [build script](../advanced_usage/custom_app.md), [data script](../advanced_usage/custom_data.md), or [helper script](../advanced_usage/custom_helper.md) works, it's worth sharing — a recipe in a shared collection is one build that serves everyone, instead of each person rediscovering the same vendor tarball.

Recipes come from **collections**: an ordered `sources` list in your config, where the first match wins. Sharing means putting a recipe in a collection other people have configured. Three ways to do it:

| Option | Reaches | Setup |
|---|---|---|
| [Open a PR](#option-1-open-a-pr-against-the-public-collection) | everyone using CondaTainer | none |
| [Shared directory](#option-2-a-shared-directory) | the same filesystem | one config line |
| [Your own URL](#option-3-your-own-url) | anywhere over HTTP | serve the layout, generate the index |

- Publish generally useful tools and public data upstream.
- For everything internal, a shared directory is the simplest: no server, edits are live immediately.
- Reach for a URL only when your users are spread across machines that don't share storage.

Every configured collection is searched, so you can keep internal recipes in a shared directory *and* upstream the general ones.

```{tip}
Before sharing either way, put the recipe in a local collection and build it once. See [Where Recipes Live](../advanced_usage/custom_app.md#where-recipes-live).
```

## Option 1: Open a PR Against the Public Collection

The public `cnt` collection ([condatainer/recipes](https://github.com/condatainer/recipes)) is read by every install, so a recipe shows up in everyone's `condatainer avail` with no configuration.

1. Fork [condatainer/recipes](https://github.com/condatainer/recipes) and branch off `main`.
2. Add your file at the path that matches its [naming convention](../manuals/build_script.md#naming-conventions).
3. Build it and confirm it works.
4. Open a PR against `main`, including the terminal output or job log from your successful build.

See its [CONTRIBUTING.md](https://github.com/condatainer/recipes/blob/main/CONTRIBUTING.md) for the full checklist.

```{note}
The index is generated by CI on merge — don't hand-edit `index/`.
```

## Option 2: A Shared Directory

For recipes that stay inside one cluster, a directory on shared storage beats any remote. CondaTainer reads a local collection directly, so there's **no index to generate and nothing to publish**. Save a file and it's available to everyone immediately.

The layout:

```
/shared/labA/recipes/
├── recipes/            # app / data / OS recipes
│   └── my-tool/1.0
└── helpers/            # helper scripts (optional)
    └── my-service
```

Add it to the group's config, ahead of the public collection:

```bash
condatainer config prepend sources lab=/shared/labA/recipes
condatainer avail my-tool     # already visible
```

Put that line in the group's shared `config.yaml` rather than asking each person to run it — see [Configure It Once for the Whole Group](#configure-it-once-for-the-whole-group).

A recipe in your collection **shadows** a same-named one in the public collection, which is how you override an upstream recipe.

```{tip}
Keep the shared directory in a git repo checked out on the filesystem. You get review and history, and a `git pull` publishes to everyone at once.
```

A helper script can also be dropped into the `helper-scripts/` directory of any [data layer](./data_layers.md), such as the group's `$CNT_EXTRA_ROOT`. It becomes launchable by everyone who reads that layer.

## Option 3: Your Own URL

Use a remote collection when your users are on machines that don't share a filesystem — several clusters, or a lab spread across institutions.

**It does not have to be GitHub.** CondaTainer fetches fixed paths under a base URL, so any plain HTTP(S) server works: an internal web server, an object-store bucket, a GitLab or Gitea raw endpoint, static hosting.

### 1. Serve the collection layout

```
<base URL>/
├── source.json         # what this collection is
├── recipes/            # app / data / OS recipes
│   ├── cellranger/9.0.1
│   └── grch38/genome/gencode
├── helpers/            # helper scripts
│   └── my-service
└── index/              # generated — see below
    ├── recipes.json.gz
    └── helpers.json.gz
```

### 2. Generate the index

HTTP has no directory listing, so `condatainer avail` and `condatainer helper --list` read the **index files**, not the recipes themselves. A collection served without them is invisible.

Copy the generators from the public collection and run them whenever a recipe changes:

- [`generate_recipe_index.py`](https://github.com/condatainer/recipes/blob/main/scripts/generate_recipe_index.py) — writes `index/recipes.json.gz`
- [`generate_helper_index.py`](https://github.com/condatainer/recipes/blob/main/scripts/generate_helper_index.py) — writes `index/helpers.json.gz`

If your host is a git forge, automate it — the public collection's [workflows](https://github.com/condatainer/recipes/tree/main/.github/workflows) regenerate and commit on every push. Otherwise run the generators as part of whatever publishes the files. Forgetting this step is the usual reason a new recipe never appears.

### 3. Point CondaTainer at it

```bash
# Any HTTP(S) server that serves the layout
condatainer config prepend sources lab=https://recipes.labA.edu/cnt

# GitHub raw content root
condatainer config prepend sources \
    lab=https://raw.githubusercontent.com/MyOrg/recipes/main
```

Then refresh and confirm your recipes appear:

```bash
condatainer update       # refresh recipe and helper indexes from every collection
condatainer avail my-tool
condatainer helper --list
```

Collections are searched in order, so your recipes shadow same-named ones in the public collection.

```{note}
CondaTainer fetches the URL unauthenticated, so anything behind a login or token won't work — a private GitHub repo included. Either serve the files somewhere your users can read without credentials, or use a [shared directory](#option-2-a-shared-directory) instead.
```

## Configure It Once for the Whole Group

Don't ask each person to run config commands. Put the settings in a `config.yaml` at the shared root and let every user pick it up: it is read automatically when CondaTainer lives in that directory, and otherwise when users set `$CNT_EXTRA_ROOT` to it (one line in a module file or a shell profile).

```yaml
# /shared/labA/condatainer/config.yaml
sources:
  - lab: /shared/labA/recipes
build:
  ncpus: 8
```

Scaffold it with:

```bash
CNT_EXTRA_ROOT=/shared/labA/condatainer condatainer config init -l extra-root
```

`sources` merges across config layers, so this adds your collection without overriding anything a user set themselves. See [Multi-Tier Setup](../manuals/configuration.md#multi-tier-setup-system--group--user).

## Sharing Built Overlays

A recipe still costs everyone a build. If you have shared storage, share the `.sqf` too — it's a single file, and CondaTainer finds it in the shared root's `images/`:

```bash
export CNT_EXTRA_ROOT=/shared/labA/condatainer   # contains images/
```

`condatainer list` then shows the overlay as installed for everyone, with no rebuild. This is worth doing for anything expensive: large data overlays, indexes, apps with long builds. To share across sites, [publish to a registry](./distribution.md) instead.
